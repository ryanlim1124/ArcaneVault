Part IIFeature proposal (tutor submission)

1. Feature name

Vault Insights — Collection Demand & Market Signal Dashboard

A staff-only business analytics dashboard that measures which collectibles are actually moving between collections, and ranks them using a composite Demand Index.

2. Purpose

The problem it solves

The assignment brief states that Arcane Vault's reason for building this prototype is to gather insight into:

  • Popular collectible items and collections
  • User activity and engagement
  • Market demand and collection trends
  • Overall interest within the collector community

Without this feature the prototype stores that information but never surfaces it. Staff can see that data exists, but cannot answer the business question the company is actually asking: is there enough real trading appetite to justify building the full marketplace?

The key insight

The required CollectionItems schema stores two quantity columns:

ColumnMeaning
StartingQuantityHow many the collector originally acquired
CurrentQuantityHow many they still hold today

There is no reason to store both unless the difference matters. That difference is the only evidence anywhere in the prototype that a collectible has left a collection — traded, sold, or given away. Aggregated across every collector, it stops being an accounting detail and becomes a measurable demand signal.

Value added

  • Converts passive collection records into a decision-making tool.
  • Directly answers all four bullets in the brief's Background section.
  • Gives Arcane Vault an evidence base for which collectible segments a future marketplace should launch with.

3. Key functionalities

3.1 The Demand Index

#ComponentWeightFormulaMeasures
1Turnover50%(ΣStart − ΣCurr) / ΣStart × 100Share that has moved on
2Collector Reach30%holders / maxHolders × 100How widely held
3Scarcity20%(1 − ΣCurr / maxRemaining) × 100How little is left
 
DemandIndex = Turnover×0.50 + ReachScore×0.30 + ScarcityScore×0.20

Why these weights: turnover carries the most weight because units physically leaving collections is the most direct evidence of demand. Reach and scarcity are supporting context — high turnover on an item only one person owns is far weaker evidence than the same turnover across eight collectors.

Why normalise: the three components sit on incompatible natural scales ("held by 8 people" vs "72% turnover"). Normalising against the strongest item makes the weighted sum meaningful.

  • "4 of 24 collectibles are in the Hot tier, suggesting genuine trading appetite worth targeting in the marketplace build."
  • "4 collectibles show almost no movement, led by SG 50th Anniversary Coin Set. These are candidates for promotion or bundling."

Two projects, one solution

ArcaneVault.WebRazor PagesPages, session cookie, UITouch the database — no DbContext at all
Why two projects instead of one?

The assignment grades a Razor Pages app and a Web API as separate deliverables, so separating them lets each be demonstrated on its own — Swagger proves the API stands alone. It also makes the boundary real rather than a convention: the web project has no DbContext reference, so it physically cannot bypass the API.

A request, end to end

Take "a collector searches their collection for 'Coins'":

  1. Browser GETs localhost:5002/CollectionItems?Search=Coins
  2. Cookie middleware reads the auth cookie → the user is collector, role User
  3. Authorisation checks the folder rule — /CollectionItems needs any signed-in user ✓
  4. IndexModel.OnGetAsync runs; Search is already populated by model binding
  5. It calls _apiClient.GetCollectionItemsAsync(userName: User.Identity.Name, search: "Coins", …)
  6. ApiClient issues GET localhost:5001/api/collectionitems?userName=collector&search=Coins&page=1&pageSize=10
  7. API builds the LINQ query, EF translates to SQL, SQLite executes
  8. Rows project into CollectionItemDto → JSON
  9. ApiClient deserialises into the Web project's mirror DTO
  10. Razor renders the table; the browser receives HTML
The browser made exactly one request, to port 5002. The hop to 5001 happened server-side. That single fact answers the CORS question, the security question, and the architecture question at once.

Schema and EF Core configuration

String primary keys

entity.HasKey(u => u.UserName);      // ArcaneVaultUsers
entity.HasKey(c => c.CategoryCode);  // Categories

EF's convention looks for Id or <Type>Id. Neither exists, so the key is declared explicitly. These are natural keys — the business value itself identifies the row. A consequence: because CategoryCode is the key and is referenced by join rows, it cannot be edited after creation.

The many-to-many with a composite key

modelBuilder.Entity<CollectionItem>()
    .HasMany(i => i.Categories)
    .WithMany(c => c.CollectionItems)
    .UsingEntity<CollectionItemCategory>(
        right => right.HasOne(cic => cic.Category)
                      .WithMany(c => c.CollectionItemCategories)
                      .HasForeignKey(cic => cic.CategoryCode)
                      .OnDelete(DeleteBehavior.Restrict),
        left  => left.HasOne(cic => cic.CollectionItem)
                     .WithMany(i => i.CollectionItemCategories)
                     .HasForeignKey(cic => cic.ItemId)
                     .OnDelete(DeleteBehavior.Cascade),
        join =>
        {
            join.ToTable("CollectionItemCategories");
            join.HasKey(cic => new { cic.ItemId, cic.CategoryCode });
        });

Three lambdas: the right foreign key, the left foreign key, then the join table itself. The composite key satisfies the specified schema and makes attaching the same category twice structurally impossible.

Why Restrict on one side and Cascade on the other?

They guard different things. Cascade on the item side is correct — if an item is genuinely deleted, its category links are meaningless. Restrict on the category side prevents deleting a category that 24 items still use, which would silently strip classification from two dozen collectors' records.

Authentication, end to end

The API owns passwords

// Registration
user.PasswordHash = _passwordHasher.HashPassword(user, input.Password);

// Login
var verification = _passwordHasher.VerifyHashedPassword(user, user.PasswordHash, input.Password);
if (verification == PasswordVerificationResult.Failed)
    return Unauthorized(new { message = failureMessage });

PasswordHasher<T> is ASP.NET Core's built-in PBKDF2 implementation with a per-user random salt. It ships in the shared framework — no extra package.

A security detail worth raising unprompted

The login failure message is identical whether the username doesn't exist, the account is deactivated, or the password is wrong. Different messages would let an attacker enumerate valid usernames.

The web app owns the session

var claims = new List<Claim>
{
    new(ClaimTypes.Name,  user.UserName),
    new(ClaimTypes.Email, user.Email),
    new(ClaimTypes.Role,  user.RoleName),   // ← drives all role checks
};

await HttpContext.SignInAsync(
    CookieAuthenticationDefaults.AuthenticationScheme,
    new ClaimsPrincipal(new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme)));

That single Role claim powers both User.IsInRole("Staff") in the navbar and the StaffOnly policy. It originates from the database and travels in a signed, encrypted cookie — the browser cannot forge it.

Authorisation declared by folder

options.Conventions.AuthorizeFolder("/CollectionItems");           // any signed-in user
options.Conventions.AuthorizeFolder("/Categories", "StaffOnly");   // administrators only
options.Conventions.AuthorizeFolder("/Insights", "StaffOnly");
Defence in depth. Hiding the Categories link is a usability measure, not a security boundary. The real boundary is the policy: signing in as collector and typing /Categories still lands on Access Denied. Demo this — it's exactly what a tutor probes.

Why the API never returns an entity

  1. Reference cycles. CollectionItem.Categories points at Category objects whose CollectionItems point back. Serialising that either throws a cycle exception or nests forever. A DTO is flat by construction, so the cycle never exists.
  2. Never leaking the hash. ArcaneVaultUser has a PasswordHash property. UserDto does not. Returning entities would ship every password hash to the browser.

Read and write DTOs are separate types: CollectionItemDto carries display data (CategoryNames, UnitsMoved); CollectionItemInputDto carries only what a form submits (CategoryCodes). Mapping is hand-written LINQ .Select(...) — no AutoMapper, one fewer dependency.

★ The Demand Index — the graded feature

The schema stores two quantity columns. There is no reason to store both unless the difference means something — and that difference is the only evidence in the whole system that a collectible has left a collection. Aggregated across collectors, it becomes a demand signal. That single observation is the entire feature.

The code

// Normalisation baselines - the strongest values present.
var maxReach     = raw.Max(r => r.CollectorReach);
var maxRemaining = raw.Max(r => r.TotalCurrent);

var unitsMoved = r.TotalStarting - r.TotalCurrent;

var turnoverRate = r.TotalStarting == 0 ? 0m
    : Math.Round((decimal)unitsMoved / r.TotalStarting * 100m, 1);

var reachScore = maxReach == 0 ? 0m
    : Math.Round((decimal)r.CollectorReach / maxReach * 100m, 1);

// Inverted - fewer units left scores higher.
var scarcityScore = maxRemaining == 0 ? 100m
    : Math.Round((1m - (decimal)r.TotalCurrent / maxRemaining) * 100m, 1);

var demandIndex = Math.Round(
      turnoverRate  * TurnoverWeight
    + reachScore    * ReachWeight
    + scarcityScore * ScarcityWeight, 1);
  • Every division has a zero guard via the ? : ternary.
  • The (decimal) casts force decimal division — without them int / int truncates and every rate comes out 0 or 1.
  • decimal not double, because these are exact reported figures.

The any-field search 3 marks

var pattern   = $"%{term}%";
var isNumeric = int.TryParse(term, out var numericTerm);

query = query.Where(i =>
       EF.Functions.Like(i.ItemName, pattern)
    || EF.Functions.Like(i.UserName, pattern)
    || i.CollectionItemCategories.Any(cic =>
              EF.Functions.Like(cic.CategoryCode, pattern)
           || EF.Functions.Like(cic.Category.CategoryName, pattern))
    || (isNumeric && (i.ItemId           == numericTerm
                   || i.StartingQuantity == numericTerm
                   || i.CurrentQuantity  == numericTerm)));
  • EF.Functions.Like becomes a real SQL LIKE — filtering runs inside SQLite, not after loading every row.
  • isNumeric short-circuits the integer comparisons, so "Charizard" never attempts a nonsensical numeric match.
  • The .Any(...) reaches through the join table into category code and name.

Demo: gundam → by name · Coins → by category · 47 → by ID.

ApiClient — the only door between the tiers

builder.Services.AddHttpClient<ApiClient>(client =>
{
    client.BaseAddress = new Uri(apiBaseUrl);   // http://localhost:5001
    client.Timeout     = TimeSpan.FromSeconds(30);
});

AddHttpClient<T> registers a typed client: a pooled HttpClient managed by IHttpClientFactory, avoiding the socket exhaustion caused by new HttpClient() per request. HTTP not HTTPS deliberately — a server-to-server HTTPS call would have to validate the dev certificate, a common setup failure, and both processes are local.

Every public method funnels through four private helpers, so failure handling is written exactly once. ExtractErrorMessageAsync handles two error shapes: the API's own { "message": … }, and [ApiController]'s RFC 9110 problem document with an errors dictionary. A total network failure becomes "Could not reach the Arcane Vault API…" — exactly what a tutor sees if they start the projects in the wrong order.

Razor Pages lifecycle

Query-string binding

[BindProperty(SupportsGet = true)]
public string? Search { get; set; }

Plain [BindProperty] binds on POST only. SupportsGet = true makes it bind from the query string too, so ?Search=gundam&PageNumber=2 populates the properties automatically — bookmarkable, with a working back button.

Checkbox arrays for the many-to-many

<input type="checkbox" name="Input.CategoryCodes" value="@option.Value"
       checked="@(Model.Input.CategoryCodes.Contains(option.Value))" />

Every checkbox shares one name, so the binder collects the ticked values into string[] CategoryCodes.

Post / Redirect / Get

  1. OnGetAsync loads dropdowns and, on Edit, the record.
  2. OnPostAsync runs. If !ModelState.IsValid the page re-renders with input intact — options reloaded first, since they aren't posted.
  3. An API rejection becomes ModelState.AddModelError(string.Empty, ex.Message) — a form-level error rendered by asp-validation-summary="ModelOnly".
  4. On success, TempData["SuccessMessage"] is set and the handler redirects. TempData survives exactly one redirect.

That redirect stops a browser refresh from re-submitting the form.

Bugs found and fixed

"Tell me about a problem you hit" is a near-certain question. These are all real.

1. SQLite cannot translate Distinct().Count() inside a GroupBy

.GroupBy(i => i.ItemName)
.Select(g => new { CollectorReach = g.Select(i => i.UserName).Distinct().Count(), … })

Compiles fine, throws at runtime: "Translating this query requires the SQL APPLY operation, which is not supported on SQLite." Fixed by fetching four narrow columns and grouping with LINQ-to-Objects. On SQL Server the original would have worked.

2. ActionResult<T>.Value is null when you return Ok(...)

The highlights endpoint reused two other endpoints by calling them and reading .Value. It silently produced nothing — .Value is only populated when an action returns T directly; wrapping in Ok(...) puts the payload in .Result. Two of the five insights never appeared, with no error. Fixed by extracting plain private methods both callers share.

3. Disabled inputs are not submitted by browsers

Input.CategoryCode = Code;
ModelState.Remove($"{nameof(Input)}.{nameof(Input.CategoryCode)}");

The Category Edit page shows the code in a disabled input. Browsers don't submit disabled fields, so binding recorded "required" against a field the user cannot see — and the ModelOnly summary never rendered it. The page silently redisplayed on save. Re-assigning isn't enough: ModelState already recorded the failure, so the stale entry must be removed.

4. Nullable reference types silently imply [Required]

.AddMvcOptions(o => o.SuppressImplicitRequiredAttributeForNonNullableReferenceTypes = true);

With <Nullable>enable</Nullable>, MVC infers [Required] for every non-nullable reference-type property. That broke UserName (set server-side, never posted) and CategoryCodes (empty when no categories ticked).

5. A seeded timestamp could land in the future

// before: Rng.Next(1, Math.Max(daysAgo, 2)) → AddDays(1) when daysAgo == 0
LastUpdatedAt = createdAt.AddDays(Rng.Next(0, daysAgo + 1))

An item generated as "added today" received a last updated date of tomorrow — visible on the details page. Caught by checking the live data rather than trusting the code.

ArcaneVault.Api/Program.cs

Wires up services, migrates and seeds the database, defines the HTTP pipeline.

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlite(builder.Configuration.GetConnectionString("DefaultConnection")));

builder.Services.AddSingleton<IPasswordHasher<ArcaneVaultUser>, PasswordHasher<ArcaneVaultUser>>();

AddDbContext registers the context as scoped — one instance per HTTP request, the right lifetime for a unit of work. The hasher is a singleton because it holds no state.

using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    db.Database.Migrate();
    DbInitializer.Seed(db, hasher);
}
  • CreateScope() is required — the context is scoped and there's no request in progress at startup.
  • Migrate() creates the file and applies pending migrations, so the tutor never runs an EF command.
  • Seed only populates an empty database.
Why Migrate() rather than EnsureCreated()?

EnsureCreated builds the schema from the model and ignores migrations entirely — you can never evolve the schema afterwards. Migrate applies the migration history, which is what the assignment asks for.

ArcaneVault.Api/Data/AppDbContext.cs

DbSets plus all key, index and relationship configuration.

public DbSet<Category> Categories => Set<Category>();

The expression-bodied form avoids a nullable warning, since the property is computed rather than assigned.

entity.Property(r => r.RoleId).ValueGeneratedNever();

Without this SQLite would auto-increment RoleId and ignore the seeder's values. RoleIds.User = 1 and RoleIds.Staff = 2 are referenced as constants, so they must be exactly those numbers.

entity.HasIndex(u => u.Email).IsUnique();
You already check for duplicate emails in the controller — why also index it?

The check is for the message; the index is for correctness. Two registrations arriving simultaneously could both pass the AnyAsync check before either saves. The index is the only thing that holds under concurrency.

Know this distinction: the skip navigation (item.Categories) is the convenient way to read categories. The explicit join entity (item.CollectionItemCategories) is what the write path manipulates, because it carries the composite key. Both exist deliberately.

private async Task<JsonResult> SafeJsonAsync<T>(Func<Task<T>> load, string panelName)
{
    try { return new JsonResult(await load()); }
    catch (ApiClientException ex)
    { return new JsonResult(new { error = ex.Message }) { StatusCode = 502 }; }
}

A generic helper taking Func<Task<T>> — a deferred async call — so all five handlers share one error path. 502 Bad Gateway is the honest code: this server is fine, the upstream one isn't.

The architectural point: these handlers are same-origin. The browser never contacts port 5001. No CORS, the API address stays server-side, and because they live in /Insights they inherit StaffOnly — the data is as protected as the page.

★ Pitching the feature (step 12)

Lead with the insight, not the UI:

"The brief gave me a schema where every collection item stores two quantities — what the collector originally acquired, and what they still hold. There's no reason to store both unless the difference means something, and that difference is the only evidence in the whole system that a collectible has actually left a collection."

"So I aggregated that gap across every collector and turned it into a Demand Index — turnover weighted at 50%, how widely held it is at 30%, and how little remains in circulation at 20%. Reach and scarcity are normalised against the strongest item, because 'held by 8 people' and '72% turnover' aren't otherwise comparable numbers."

"And the Background section of the brief says Arcane Vault wants to understand popular items, engagement, and market demand before committing to the marketplace. This answers all of that from the prototype's own data."

Then point at the Charizard row — your best single moment:

"Charizard actually has the higher turnover than the item above it — 78.4% versus 75% — but a lower index, because it's held by one fewer collector and reach is 30% of the score. If I'd just sorted by turnover the ranking would be the other way round and the business would have been told the wrong thing. That trade-off is the whole reason it's a composite metric."

Questions you should expect

"Why two separate projects instead of one?"

The assignment grades a Razor Pages app and a Web API as separate deliverables, so separating them lets each be demonstrated independently — Swagger proves the API stands alone. It also enforces a real boundary: the web project has no DbContext, so it physically cannot bypass the API.

"Why doesn't the browser call the API directly?"

Three reasons. No CORS configuration is needed, because the browser only talks to port 5002 and the cross-port hop happens server-to-server. The API's address never reaches the client. And the dashboard's data handlers inherit the page's StaffOnly policy.

"Why did you add columns to the schema?"

Three columns. PasswordHash is a necessity — the brief requires login, impossible without storing a credential. CreatedAt and LastUpdatedAt power the activity chart and the 30-day engagement metric. The brief explicitly permits adding columns for the feature, and no specified column, key or relationship was changed.

"Why soft delete on items but hard delete on categories?"

It follows the schema. CollectionItems has an IsDeleted column and Categories doesn't — so items are hidden rather than destroyed, which also preserves the demand history. Categories are genuinely removed but protected by a Restrict foreign key.

"Where does the role come from — could a user fake it?"

No. At login the API verifies the password and returns the role from the database. The web app writes it into a Role claim inside a signed, encrypted cookie the browser can't read or forge. And self-registration always assigns the User role in the API, so a visitor can't grant themselves Staff even by tampering with the form.

"Tell me about a problem you ran into." (near-certain)

Lead with the SQLite one — it's the most technical. The demand aggregation originally counted distinct owners inside a GroupBy. It compiles fine but throws at runtime because SQLite can't express that without the APPLY operation. Fixed by fetching four narrow columns and grouping in memory.

If they want a second, the ActionResult<T>.Value one is good: two insights silently never appeared because .Value is null when you return Ok(...). All five bugs are in Part III.

"Why those weights? Why not equal thirds?"

Because the components aren't equally strong evidence. Units physically leaving collections is a direct observation; reach and scarcity qualify it. High turnover on an item one person owns is much weaker evidence than the same turnover across eight collectors. The weights are named constants at the top of the controller, so they're a tunable business decision rather than magic numbers.

"How would you extend this?"

The biggest limitation is that collectibles are matched by name, because the prototype schema has no shared catalogue table. A real version would add a master Collectibles table so two people owning the same card reference the same row. Beyond that, the Demand Index is the natural input to the trade-matching engine the marketplace would need.

If something breaks mid-demo

  • "Could not reach the Arcane Vault API" — the API isn't running. Start it; the page recovers on refresh. Say it out loud: "that's the ApiClient's friendly error handling rather than an unhandled exception."
  • Dashboard empty — delete arcanevault.db*, restart the API, refresh.
  • Port in use — an old instance is running. Kill it, or change the ports in launchSettings.json and ApiBaseUrl together.

C# syntax you'll be asked about

async Task<T> / await

Marks a method asynchronous; await pauses until the database or HTTP call completes without blocking the thread.

=> expression body

Shorthand for a method whose body is a single expression. Used throughout ApiClient.

is not null

Pattern-matching null check, preferred over != null because it can't be affected by an overloaded ==.

[] collection expression

C# 12 shorthand. = []; replaces = Array.Empty<T>().

record

Used for RawSignal — a small immutable value carrier. DTOs stay plain classes because the model binder mutates them.

switch expression

demandIndex switch { >= 60m => "Hot", … } — relational patterns banding a number into labels.

EF.Functions.Like

Translates to a real SQL LIKE so filtering runs inside SQLite.

FindAsync vs FirstOrDefaultAsync

FindAsync looks up by key and checks the change tracker first. FirstOrDefaultAsync always queries and is needed with .Include(...).

nameof(...)

Compile-time reference to a member's name, so renaming can't silently break a route or ModelState key.

?. and ??

Null-conditional and null-coalescing. User.Identity?.IsAuthenticated won't throw when there's no identity.

ClaimTypes.Role

The claim User.IsInRole("Staff") and the StaffOnly policy both read. Set once at login from the database.

Url.IsLocalUrl(...)

Guards the login ReturnUrl against open-redirect attacks.
